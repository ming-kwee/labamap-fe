# Frontend Validation Rules Implementation Guide

## Overview

This document outlines the comprehensive validation framework for the omnichannel ecommerce platform, detailing how frontend applications should integrate with the MongoDB-based validation system. The validation system consists of three main collections that work together to provide dynamic, rule-based validation.

## MongoDB Collections Analysis

### 1. ecommerce_form_schemas Collection

**Purpose**: Stores generated dynamic form schemas with field definitions, validation rules, and conditional logic.

**Key Fields**:
- `schema_key`: Unique identifier (format: `userId_organizationId_category_channels`)
- `user_id`, `organization_id`: Multi-tenancy support
- `product_category`: Category-specific schema generation
- `target_channels`: Channel-specific field requirements
- `fields`: Array of field definitions with validation rules
- `conditional_logic`: Dynamic field behavior rules
- `metadata`: Additional validation configuration

**Frontend Usage**: Primary source for dynamic form generation and field-level validation rules.

### 2. ecommerce_business_rules Collection

**Purpose**: Stores business logic validation rules for data processing, enhancement, and validation.

**Key Fields**:
- `rule_type`: PRE_PROCESSING, BUSINESS_LOGIC, DATA_ENHANCEMENT
- `priority`: Execution order
- `applicable_fields`: Fields this rule applies to
- `validation_rules`: Field-specific validation logic
- `transformation_rules`: Data transformation logic
- `applicable_categories`, `supported_channels`: Scope limitations

**Frontend Usage**: Defines complex business validation logic that goes beyond basic field validation.

### 3. ecommerce_conditional_logic_rules Collection

**Purpose**: Stores conditional logic for dynamic form behavior (show/hide fields, conditional validation).

**Key Fields**:
- `trigger_field`, `trigger_value`, `trigger_operator`: Condition definition
- `condition_type`: SHOW, HIDE, REQUIRE, OPTIONAL, VALIDATE, TRANSFORM
- `affected_fields`: Fields affected by the condition
- `conditions`: Complex condition expressions
- `actions`: Actions to perform when conditions are met

**Frontend Usage**: Implements dynamic form behavior and conditional field validation.

```http
POST /api/v1/ecommerce/form-schema/generate
```


**Purpose**: Refresh schema when product category changes
**Use Case**: Dynamic field loading based on category selection

### 2. Product Validation APIs


**Purpose**: Comprehensive validation using business rules engine

- Multi-layer validation (field-level + business logic)

- Performance scoring and validation metrics


**Purpose**: Basic field validation and legacy compatibility


**Purpose**: Schema-based validation for dynamic forms

#### Test Rules Execution

**Purpose**: Test rule execution without creating products
**Use Case**: Validation testing and rule debugging


**Purpose**: Apply data transformations without full validation
**Use Case**: Preview data enhancements before submission

## Frontend Validation Implementation Steps

### Step 1: Initial Form Schema Generation

```javascript
// 1. Request form schema based on user context
const schemaRequest = {
  context: {
    userId: "user123",
    organizationId: "org456",
    userRole: "BUSINESS_USER", 
    productCategory: "electronics", // Optional initially
    targetChannels: ["shopify", "amazon"],
    permissions: ["CREATE_PRODUCT", "EDIT_PRODUCT"]
  }
};

const schemaResponse = await fetch('/api/v1/ecommerce/form-schema/generate', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(schemaRequest)
});

const { formSchema } = await schemaResponse.json();
```

### Step 2: Dynamic Form Generation

```javascript
// 2. Build form from schema
function buildFormFromSchema(schema) {
  const formFields = schema.fields.map(field => ({
    id: field.id,
    type: field.type,
    label: field.label,
    required: field.required,
    validation: field.validation,
    conditionalLogic: field.conditionalLogic,
    options: field.options, // For select/radio fields
    placeholder: field.placeholder,
    helpText: field.helpText
  }));

  // Apply conditional logic rules
  applyConditionalLogic(formFields, schema.conditionalLogic);
  
  return formFields;
}
```

### Step 3: Real-time Field Validation

```javascript
// 3. Implement field-level validation
async function validateField(fieldId, value, formData) {
  // Client-side validation first (immediate feedback)
  const field = getFieldDefinition(fieldId);
  const clientValidation = validateClientSide(field, value);
  
  if (!clientValidation.valid) {
    return clientValidation;
  }

  // Server-side validation for complex rules
  const validationRequest = {
    fieldId: fieldId,
    value: value,
    context: {
      category: formData.category,
      channelId: getCurrentChannel(),
      allFieldValues: formData
    }
  };

  const response = await fetch('/api/v1/category-configuration/validate-field', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(validationRequest)
  });

  return await response.json();
}
```

### Step 4: Conditional Logic Implementation

```javascript
// 4. Handle conditional field behavior
function applyConditionalLogic(fields, conditionalRules) {
  conditionalRules.forEach(rule => {
    const triggerField = fields.find(f => f.id === rule.triggerField);
    const affectedFields = fields.filter(f => 
      rule.affectedFields.includes(f.id)
    );

    // Listen for trigger field changes
    triggerField.addEventListener('change', (event) => {
      const triggerValue = event.target.value;
      const shouldTrigger = evaluateCondition(
        triggerValue, 
        rule.triggerValue, 
        rule.triggerOperator
      );

      if (shouldTrigger) {
        executeConditionalActions(affectedFields, rule.actions);
      }
    });
  });
}

function executeConditionalActions(fields, actions) {
  actions.forEach(action => {
    const targetField = fields.find(f => f.id === action.targetField);
    
    switch(action.actionType) {
      case 'SHOW_FIELD':
        targetField.style.display = 'block';
        break;
      case 'HIDE_FIELD':
        targetField.style.display = 'none';
        break;
      case 'REQUIRE_FIELD':
        targetField.setAttribute('required', 'true');
        break;
      case 'OPTIONAL_FIELD':
        targetField.removeAttribute('required');
        break;
      case 'SET_VALUE':
        targetField.value = action.actionValue;
        break;
    }
  });
}
```

### Step 5: Category-Based Schema Refresh

```javascript
// 5. Handle category changes
async function handleCategoryChange(newCategory) {
  const refreshRequest = {
    context: {
      ...currentContext,
      productCategory: newCategory
    }
  };

  const response = await fetch('/api/v1/ecommerce/form-schema/refresh', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(refreshRequest)
  });

  const { formSchema } = await response.json();
  
  // Update form with new schema
  updateFormFields(formSchema);
  
  // Preserve existing values where possible
  preserveCompatibleValues(formSchema);
}
```

### Step 6: Comprehensive Form Validation

```javascript
// 6. Final form validation before submission
async function validateCompleteForm(formData) {
  // Step 1: Client-side validation
  const clientValidation = validateAllFieldsClientSide(formData);
  if (!clientValidation.valid) {
    showValidationErrors(clientValidation.errors);
    return false;
  }

  // Step 2: Enhanced server validation with business rules
  const validationRequest = {
    name: formData.name,
    sku: formData.sku,
    category: formData.category,
    price: formData.price,
    description: formData.description,
    attributes: formData.attributes,
    // ... all form fields
  };

  const response = await fetch('/api/v1/products/enhanced/validate', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(validationRequest)
  });

  const validationResult = await response.json();

  if (!validationResult.valid) {
    showBusinessRuleViolations(validationResult.violations);
    showWarnings(validationResult.warnings);
    return false;
  }

  // Step 3: Show warnings if any (but allow submission)
  if (validationResult.hasWarnings) {
    showWarnings(validationResult.warnings);
  }

  return true;
}
```

### Step 7: Error Handling and User Experience

```javascript
// 7. Enhanced error handling
function showValidationErrors(errors) {
  errors.forEach(error => {
    const fieldElement = document.getElementById(error.fieldId);
    const errorElement = createErrorElement(error.message);
    
    fieldElement.classList.add('validation-error');
    fieldElement.parentNode.appendChild(errorElement);
    
    // Auto-clear error on field change
    fieldElement.addEventListener('input', () => {
      clearFieldError(fieldElement);
    });
  });
}

function showBusinessRuleViolations(violations) {
  const violationContainer = document.getElementById('business-rule-errors');
  
  violations.forEach(violation => {
    const violationElement = createViolationElement({
      message: violation.message,
      severity: violation.severity,
      ruleId: violation.ruleId,
      affectedFields: violation.affectedFields
    });
    
    violationContainer.appendChild(violationElement);
    
    // Highlight affected fields
    violation.affectedFields.forEach(fieldId => {
      const field = document.getElementById(fieldId);
      field.classList.add(`violation-${violation.severity.toLowerCase()}`);
    });
  });
}
```

## Integration Best Practices

### 1. Performance Optimization

- **Schema Caching**: Cache form schemas client-side with TTL
- **Debounced Validation**: Implement debouncing for real-time field validation
- **Progressive Loading**: Load validation rules as needed, not all at once
- **Error Recovery**: Graceful fallback to basic validation if APIs are unavailable

### 2. User Experience Guidelines

- **Immediate Feedback**: Show validation errors as users type (with debouncing)
- **Clear Error Messages**: Use business-friendly error messages from the API
- **Progressive Disclosure**: Show advanced validation options based on user role
- **Visual Indicators**: Use consistent styling for different validation states

### 3. Error Handling Strategy

- **Network Failures**: Cache validation results and retry failed requests
- **API Timeouts**: Fall back to client-side validation with user notification
- **Invalid Schemas**: Provide graceful degradation to basic form structure
- **Business Rule Conflicts**: Show clear resolution paths to users

### 4. Multi-tenancy Considerations

- **Context Awareness**: Always include organization and user context in API calls
- **Permission Checking**: Validate user permissions before showing advanced features
- **Channel Specificity**: Adapt validation rules based on target sales channels
- **Data Isolation**: Ensure validation rules respect organizational boundaries
