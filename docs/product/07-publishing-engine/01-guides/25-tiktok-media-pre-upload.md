# 25 — TikTok Shop media pre-upload (fixing `12052300 product_image_uri invalid`)

**Status:** implemented (bff-v14). **Area:** publish pipeline → sync-service MEDIA_PRE step.
**Symptom fixed:** TikTok create returns HTTP 200 with
`{"code":12052300,"message":"Parameter product_image_uri[0] is invalid because product image URI must be generated by Upload Product Image API..."}`.

Follows [[24-tiktok-publish-signing]] (signing) and the variantGroups fix — this is the **next**
gate after those pass.

---

## 1. What the error actually means

TikTok 202309 create does **not** accept an external image URL (our GCS URL). Every image must first
be uploaded through the **Upload Product Image API** (`POST /product/202309/images/upload`), which
returns a **TikTok-internal URI**; only that URI may appear in the create body's `main_images`.

So the images were **not missing** — post-processing put them into `main_images` correctly (two GCS
URLs were present in the payload). The problem is they were **raw URLs**, never pre-uploaded.

### Why the pre-upload step was skipped

The sync-service runs a **MEDIA_PRE loop** before create_CP. That loop looks up **one exact metadata
key**:

```
sync Constants: INSTRUCTION_SETUP__WORKACTION$CREATE_CP_MEDIA_PRE = "instruction.setup:workaction#create_CP_Media_Pre"
```

The BFF was authoring the step under `workaction#upload_image` — a key **no loop reads**. Result in
the sync log:

```
[workflow] entering media_pre loop
[workflow] media_pre - no metadata key, skipping loop      ← step silently skipped
...
[HTTP] response ... "code":12052300 ... product_image_uri[0] is invalid
```

The raw GCS URLs went straight into create → rejected. This is the identical pattern to Shopee, which
already ships `workaction#create_CP_Media_Pre` and works.

---

## 2. The fix (BFF, `config/ChannelMetadataMigration.java`)

Renamed the step to the key the sync loop actually reads, and gave it the full reshape/write-back
logic (the old `upload_image` value had only a stub `response-update-to` and no body reshaping).

**Registration** (`buildTiktokshopMetadata`):
```java
.key("workaction#create_CP_Media_Pre")          // was: workaction#upload_image (never read)
.value(tiktokshopCreateMediaPreWorkflow())
```

**Workflow value** (`tiktokshopCreateMediaPreWorkflow`) — a JSON **array** of one endpoint step,
mirroring the verified `tiktok_create_product_e2e_payload.json`:

```json
[{
  "endpoint": {
    "url": "https://open-api.tiktokglobalshop.com/product/202309/images/upload",
    "method": "POST", "action": "ON_REST_CREATE", "contentType": "multipart/form-data",
    "headers": { "x-tts-access-token": "token" },
    "params":    { "app_key": "app_key", "timestamp": "TIMESTAMP" },
    "signature": { "paramOrder": ["app_key","timestamp"],
                   "formula": "${SECRET}${PATH}app_key${app_key}timestamp${timestamp}${BODY}${SECRET}",
                   "algorithm": "HmacSHA256", "includeBody": false }
  },
  "body-reshape-to": {
    "from": "main_images", "mappings": { "uri": "uri" },
    "output": { "fields": { "uri_key": "data" }, "conversion": { "uri_key": "Base64" } }
  },
  "response-update-to": {
    "responsePaths": ["[*].data.uri"],
    "transformPaths": [ { "main_images": [ { "operation": "shift",
                          "spec": { "*": { "data": { "uri": "[&2].uri" } } } } ] } ],
    "updatePaths": [ { "get": "main_images", "to": "main_images", "in": "attribute" } ]
  }
}]
```

What each part does:
- **endpoint** — the image-upload call. **Not shop-scoped** (no `shop_cipher`) and the multipart body
  is **not** signed → `tiktokSignedParams(false)` + `tiktokSignature(false, false)` (see [[24-tiktok-publish-signing]]).
- **body-reshape-to** — for each `main_images[uri]`, download the URL and send it Base64-encoded as
  the multipart field `data` (`conversion: uri_key → Base64`).
- **response-update-to** — rebuild the whole `main_images` attribute from the aggregated upload
  responses (see §2b for why it must be shaped this way).

Signing reuses the two helpers from guide 24 — no new signing code, no channel branch.

### 2b. The write-back trap: `Unsupported attribute type:` (empty type)

The first cut used `to: "main_images[*].uri"` with no `transformPaths` — mirroring the e2e payload
file. It uploaded fine but then create_CP failed:

```
[response-update-to] aggregated set attribute 'main_images[*]' = [{"code":0,"data":{...}}, {...}]
create_rest_channel_product ERROR: 400 {"error":"Unsupported attribute type: "}
```

Because `responsePaths` contains `[*]`, the sync takes its **aggregated** write-back branch
(`applyAggregatedResponseUpdate`), which behaves differently from the per-response branch:

1. `attrName = to.split(".")[0]` → for `to="main_images[*].uri"` that is the literal
   **`"main_images[*]"`**, not `main_images`.
2. It looks up a JOLT spec in **`transformPaths`** keyed by `get`. With none present, it writes the
   **raw response array** (`[{code,data,…}]`) instead of extracting `data.uri`.
3. `setAttributeValueInList` finds no attribute named `main_images[*]`, so it **adds a new one with a
   null `chnlAttrType`**. At create, `Utils.typeConverter("", …)` throws `Unsupported attribute type:`.

So the e2e payload's media-pre `response-update-to` would fail against this sync build too — it was
never actually validated end-to-end. The **working** reference is Shopee's media-pre, which supplies:

- a **`transformPaths`** JOLT keyed by `get` that reshapes the response list into the attribute's
  final value, and
- a **bare** `to` whose first dotted segment is a **real** attribute name.

The corrected TikTok write-back does the same:
- **`transformPaths`** — `{"*":{"data":{"uri":"[&2].uri"}}}` turns the response array
  `[{data:{uri:"tos-A"}}, {data:{uri:"tos-B"}}]` into `[{uri:"tos-A"}, {uri:"tos-B"}]` — the exact
  `object[]` shape `main_images` already holds (`[&2]` climbs from the `uri` leaf up to the array
  index).
- **`get: "main_images"`** matches the transformPaths key.
- **`to: "main_images"`** → `attrName = "main_images"` → updates the existing attribute **in place**,
  preserving its `chnlAttrType: "object[]"`. No junk `main_images[*]` attribute, no null type.

Result: create_CP sends `main_images: [{uri:"tos-…"}, {uri:"tos-…"}]` (TikTok URIs).

## 3. Scope: product images only (for now)

This product's SKUs have plain `sales_attributes` (`[{name:Size,value_name:Xs},{name:Color,...}]`)
with **no `sku_img`**, so per-variant image pre-upload is not needed here. When a variant carries an
image, TikTok needs it inside `sales_attributes[].sku_img.uri`, uploaded via a separate
**`workaction#create_CP_Variants_Media_Pre`** step (present in the e2e payload). That is a follow-up;
add it the same way (array workflow, `from: sales_attributes`, write back to
`skus.sales_attributes[*].sku_img.uri`, `in: variants`) when variant images are required.

## 4. Re-seed & verify

`applyChannelMetadata` (Order 100): a **system-default** config is overwritten (the new key lands on
restart); a **user-customised** config is **merge-by-key** — `create_CP_Media_Pre` is a *new* key so
it is added, and the stale `upload_image` key remains but is **inert** (no loop reads it). If you want
it gone, null `channelMetadataList` or `$pull` the `upload_image` key and restart.

```js
// mongosh — confirm the media-pre key exists and is an array workflow
db.channel_configuration.findOne(
  { channelId: "tiktokshop" }, { channelMetadataList: 1 }
).channelMetadataList.find(m => m.key === "workaction#create_CP_Media_Pre").value
```

Success in the sync log:
```
[workflow] entering media_pre loop
[HTTP] POST .../product/202309/images/upload      → 200 {"code":0,"data":{"uri":"tos-..."}}   (×N images)
[workflow] create_rest_channel_product
[HTTP] POST .../product/202309/products           → 200 {"code":0,"data":{"product_id":"..."}}
Workflow ... terminal state: COMPLETED
```

The create body's `main_images[*].uri` will be `tos-...`/TikTok URIs, not `storage.googleapis.com`.
